## Measurements

Probes: `scripts/video-probes/applelogprobe.swift` (format description, timing, metadata) and `scripts/video-probes/applelogcodes.swift` (what a custom compositor receives, and which frame), plus ffmpeg 8.1.2 and PyOpenColorIO 2.5.2. All of them only read the files; outputs went to a scratch folder.

**Format and tags (both clips).**

- ProRes 422 HQ (`apch`), 3840×2160, 10-bit 4:2:2, **video range** (no `FullRangeVideo` extension; ffprobe `tv`). The extension's `BitsPerComponent` says 12. The decode is 10-bit.
- Primaries and matrix **BT.2020**. There is **no transfer-function tag** (ffprobe `unknown`).
- **`LogTransferFunction` = `com.apple.rec2020.apple-log`** (Apple Log, not Apple Log 2).
- Make Apple, model iPhone 15 Pro, software 26.6.2. Timed-metadata tracks: video orientation, detected faces, Live Photo info, segment identifier.
- `preferredTransform` is the identity for both (landscape). Rotation is untested.
- **24 fps** (not the 30 fps the plan asked for), time base 1/600, so each frame lasts 25/600 s. **IMG_0001 has one irregular frame:** decode index 213 at 8.877 s follows a 26/600 s step. Its nominal rate is 23.998, and every later frame sits 1/600 s off the 24 fps grid. IMG_0002 is regular.

**Code values through the compositor.** The compositor asks for `[xf22, x422, 420v, 420f]` and receives **`x422`, IOSurface-backed**, for every frame. On an 8×8 grid in frames 0, 100, 200 and 212, its codes are **identical** to a plain track read, both with the composition's color properties at Rec. 709 (our default) and at BT.2020. They are within **1 code of ffmpeg's** independent ProRes decode (`yuv422p10le`). AVFoundation therefore does not color-convert Apple Log for a Rec. 709 composition, and the plan's escalation does not apply.

**Frame identity.** From the irregular frame on, the composition frame at k/24 s receives source frame **k − 1**: frames 214, 300 and 600 got 213, 299 and 599, at both color settings. The frame model maps source frame N to N × 1/24 s, and AVFoundation shows the last sample at or before the requested time. A sample 1/600 s late is therefore missed, and every cut after 8.9 s into this clip lands one frame early. This is not specific to Apple Log. Any source with an irregular timestamp is affected. The S5 files are regular, which is why G6 passed.

ProRes decoding itself is fast on the M1. The M1's missing ProRes engine only affects encoding (Task 8: 8.8 fps).

The same link limits the S5 measurements. `P1107157` is 151 Mb/s (about 19 MB/s at 24 fps), so reading it at 47 fps needs about 37 MB/s, which is the link's ceiling. Task 0's "about 47 fps decode ceiling", and G1's 38 fps bar derived from it, were very likely set by the cable, not the decoder. G1, G6's timing and G12 need a re-run with the drive at USB 3 or faster.

**OCIO 2.5.2.** Built-ins: `APPLE_LOG_to_ACES2065-1` and `CURVE - APPLE_LOG_to_LINEAR`. The studio config has an `Apple Log` color space (aliases `apple_log`, `ocio:applelog_rec2020_scene`). With ACES2065-1 → linear Rec. 709 after it, the GPU form needs **one 2D lookup texture** (4096 × 17, red, linear interpolation), unlike V-Log, which needs none. The MSL compiles at run time on the M1 in 266 ms. On 4 096 inputs the GPU matches OCIO's lossless CPU processor within 3.4e-7.

**Curve and range.** By OCIO's inverse, 18% grey is input 0.4883. If the file's video range is normalized as usual (code 64 → 0, 940 → 1), that is code 491.7; read as full scale (code/1023), it is 499.5. Without a grey card, and without Apple's white paper (which must be the source for the curve constants, not memory), the clip cannot show which normalization is right. **NOT VERIFIED.**

## Apple's LUTs and white paper (added the same day)

The owner downloaded Apple's `AppleLog-LUTs-v1.0` and the *Apple Log Profile White Paper* (September 2023, version 1.1) into `/Volumes/ExSSD1/Developer/LUTs/`. Neither is redistributed.

- **Curve.** The white paper defines the decoding function on a pixel value P normalized to [0, 1]: R = 2^((P − δ)/γ) − β for P ≥ Pt; √(P/c) + R0 for 0 ≤ P < Pt; R0 below 0. The constants are R0 = −0.05641088, Rt = 0.01, c = 47.28711236, β = 0.00964052, γ = 0.08550479, δ = 0.69336945, and Pt = c(Rt − R0)². Its reference table gives 0% → 0.150477, 18% → 0.488272, 90% → 0.681686 and 1200% → 1.0. Color is BT.2020 primaries with a D65 white, and the BT.2020 Y'CbCr formula.
- **Agreement.** OCIO's built-in inverse gives 0.15048, 0.48827 and 0.68169 for 0%, 18% and 90%. Apple's `AppleLogToLin-v1.0.cube` (`LUT_1D_SIZE 4096`) equals the white paper's decoding function at P = i/4095 within 1.1e-5 relative. The curve constants are therefore confirmed three ways, and 13.3's Double oracle takes them from the white paper.
- **Apple's Rec. 709 LUT.** `AppleLogToRec709-v1.0.cube`: `TITLE "Apple Log to Rec709 3DLUT - v1.0"`, `LUT_3D_SIZE 65` (exactly the parser's upper limit), no `DOMAIN` lines, so 0–1. Use it as `PME_APPLELOG_LUT`.
- **Normalization.** The white paper only says P is normalized to [0, 1]. Its "10-bit, full range" column (18% at code 500) shows full-range quantization, while these files are flagged video range. The clips have no black (darkest luma code 227) and nothing clipped (brightest 821), so they cannot tell the two readings apart: black would sit at 196 under the usual 64–940 decode and at 154 under code/1023. Core Image does not recognize Apple Log (it tags the frame sRGB), so it is no oracle either. **Decision:** decode the file's own video range as usual (P = the decoded R'G'B'). This is how hosts apply Apple's LUTs to video-range ProRes. It is still to be confirmed with a grey card (18% should land near code 492) or a lens-cap black (near code 196).

## Decisions

1. **Detection** reads `kCMFormatDescriptionExtension_LogTransferFunction`. `com.apple.rec2020.apple-log` means Apple Log / BT.2020 (`detectedFrom` `log-transfer-key`). The device-model fallback is not needed: the key is present on real clips. Apple Log 2 is detected only to show a hint. It was not found on the 15 Pro.
2. **Composition color stays Rec. 709.** The compositor receives `x422` code values untouched. Decode uses the BT.2020 matrix and video range.
3. **No proxy-first rule for Apple Log.** The M1 decodes 4K ProRes 422 HQ at about 105 fps, and the compositor runs at 99 fps. Proxies follow the normal proxy setting. G12's bar is 85% of the internal-disk ceiling (about 90 fps). A drive too slow for the data rate is a setup problem; the app could warn about it later.
4. **Frame exactness for irregular timestamps** gets its own fix before Apple Log ships (new item 13.2b): map source frames to the samples' real times. The simplest candidate is to request each source frame half a frame late, which is exact while drift stays under half a frame. Fix it test-first with a fixture that has one long frame. G6 gets an iPhone case.
5. **OCIO generator:** 13.3 must add 2D-texture tables (linear sampling) to `generate-shaders.py` and `OCIOColorKernels`, then the `APPLE_LOG_to_ACES2065-1` transform.
6. **Normalization:** 13.3 uses the file's own video-range decode as P (see "Apple's LUTs and white paper"). A grey-card or lens-cap clip still has to confirm it.
